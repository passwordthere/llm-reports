三款开源 MoE 模型社区评价证伪报告

Gemma 4 26B-A4B · Qwen 3.5 35B-A3B · Qwen 3.6 35B-A3B　|　数据范围：2026 年 4 月发布 ~ 2026 年 5 月中旬社区反馈
距离 gemma4 和 qwen3.5 和 qwen3.6 发布已经过去很长一段时间了，帮我收集一下社区对 gemma-4-26b-a4b, qwen3.5-35b-a3b, qwen3.6-35b-a3b 生成质量的真实评价，注意从人们的表达中通过可不可、容不容易证伪来分辨真实性筛选，最后生成 html 汇报，着重证伪思路，真实数据和结果分析。

一、证伪方法学：为什么大部分社区评价应该被打折

开源 LLM 的社区评价被三种污染严重：① 官方/合作博客的软文（包装成第三方"评测"）；② 没复现条件的 vibes 帖（"感觉变聪明了"）；③ 厂商自报基准（可能训练时见过测试集）。本报告按可证伪等级对每条评价分类，原则：

等级判定条件处理
A 级 · 高可证伪同时给出：① 具体硬件 ② 量化版本 ③ 具体 prompt 或 task ④ 观察输出 ⑤ 与对照组对比，且任何人能在自家机器复跑视为事实采纳
B 级 · 部分可证伪有具体测试细节，但单一来源、未被第二方复现；或基准分数可信但易被训练集污染谨慎采纳，标注来源
C 级 · 不可证伪"感觉""明显更强""碾压"类形容；没说硬件/量化/prompt；评论者也是发布方的合作生态舍弃，仅用于了解情绪

核心判别问句：这条评价如果是假的，我能用什么动作把它证伪？如果想不出动作，它就是 C 级。

三、A 级证据：可复现的社区报告

判定标准：报告人指明硬件、量化、prompt、对照组，并提供了 issue/blog 中的具体配置文件或截屏。读者可以拿同一份配置跑出同样结果。

A1 · Gemma 4 26B-A4B：MoE 速度优势是真的

来源：Hacker News 评论（id=47616761，用户 GistNoesis）；XDA Developers 评测

设置：RTX 4090 24GB，llama.cpp + GGUF Q4

对照吞吐
Gemma 4 31B（dense）~5 tok/s
Gemma 4 26B-A4B（MoE，激活 3.8B）~150 tok/s
Qwen 3.5 35B-A3B（MoE，激活 3B）~100 tok/s

因果：解码速度卡在每个 token 要从显存读多少权重，所以决定速度的是激活参数而不是总参数。3.8B × 4bit ≈ 1.9 GB/token，4090 带宽 ~1 TB/s，理论上限好几百 tok/s，实测 150 tok/s 完全合理。

结论：真 这是 MoE 架构的直接物理后果，不是模型质量信号——别拿"我的 26B-A4B 跑得飞快"推论"它比 31B 强"。

A2 · Qwen 3.5 35B-A3B：MLX 4bit 多轮工具调用退化（GitHub Issue #1011）

来源：ml-explore/mlx-lm Issue #1011

设置：Mac Studio M4 Max 128GB，macOS 15.4，mlx-community 4bit / 8bit checkpoint，70 轮多轮 tool-calling 对话

变体退化轮次表现
mlx-community 4bit第 5 轮不再输出结构化 tool_use block，退化为纯文本 [Tool call: search_files(...)]
mlx-community 8bit第 13 轮同上
GGUF Q4_K_XL（llama.cpp）70/70结构化输出全程稳定
云端 FP（满精度）70/70结构化输出全程稳定

因果：mlx 框架在 KV cache 量化路径上有 bug → 长上下文里"开 tool_use block"的低概率 token 被压平 → 模型转而采样高频替代（人话写法）。同模型换 llama.cpp 完全正常说明不是权重的锅。

结论：真 但责任在框架/量化路径，不是基座模型本身。Mac 用户用 Qwen 系列做 agentic 任务请避开 mlx-community 量化，走 GGUF 或全精度。

A3 · Qwen 3.6 35B-A3B：vLLM 上 looping bug（生产环境）

来源：David Vassallo 博客 (2026-05-02)

设置：自托管 RedHatAI/Qwen3.6-35B-A3B-NVFP4 + vLLM nightly + MTP（multi-token prediction 投机解码）开启 + streaming

症状：模型在 tool-call 场景里同一组 token 无限重复。

逐步定位：

  • 关闭 MTP（即关闭投机解码）→ loop 不再被流式路径触发
  • 把 kv-cache 改 fp8 量化 → "失败也算成功"，量化误差反而阻止 token 锁死
  • 最终稳态：repetition_penalty=1.1、presence_penalty=0、开 prefix caching + chunked prefill

因果：vLLM 在 streaming + MTP 路径上的回归 bug，影响所有走该路径的模型，恰好在 Qwen3.6 上被踩到。

结论：真但归属在框架 生产用 Qwen 3.6 上 vLLM 必须钉版本，nightly 当前不稳。

A4 · Simon Willison 的 pelican-on-bicycle 测试（笑话基准）

来源：simonwillison.net (2026-04-16)

设置：MacBook Pro M5 + LM Studio + Qwen3.6-35B-A3B-UD-Q4_K_S.gguf（20.9 GB）；对照 Opus 4.7 via API

主测：让模型生成"鹈鹕骑自行车"的 SVG；反过拟合二次验证：换成"火烈鸟骑独轮车"。

结论原话："I'm giving this one to Qwen 3.6. Opus managed to mess up the bicycle frame!"

Simon 自己怎么定调这条证据："the pelican benchmark has always been meant as a joke ... today, even that loose connection to utility has been broken."

结论：真但弱 单一定性样本，作者本人否认它能推论"Qwen 3.6 > Opus 4.7"。是一个反例而非趋势。

污染怀疑：MMLU/AIME/SWE-bench 公开题集都可能在训练集里出现。LiveCodeBench 因为按发布日期截断、Arena AI 因为是匿名 head-to-head 投票，被认为更抗污染——两者上 Gemma 和 Qwen 都没拉开数量级差距。

结论：谨慎 只看抗污染基准时，两家差距远小于各自 PR 稿里描述的"碾压"。

B2 · "27B dense 反超 35B-A3B"（Qwen 官方自己披露）

Qwen 在 3.6-27B 发布时给出的官方对比表显示：27B dense 在每一项基准上都超过 35B-A3B，SkillsBench 高 15.5 分、Terminal-Bench 高 7.8 分、SWE-bench 高 3-4 分。

因果：35B-A3B 激活 3B，27B-dense 激活 27B——后者每个 token 看到的有效计算量是 9 倍。MoE 的卖点是"在同等吞吐下追求更高质量上限"，但当你接受 dense 的低吞吐时，它的样本效率仍然更高。

结论：真 来源是 Qwen 自家——他们没有动机黑自己的 35B-A3B，这条数据反而异常可信。选 35B-A3B 是用质量换吞吐，不是免费午餐。

B3 · Gemma 4 26B-A4B 的工具调用是原生设计

XDA Developers 评测者指出，Google 给 Gemma 4 烧了 6 个专门的 special token 进 tokenizer 用于 function calling。这是可证伪的结构性事实：去看 tokenizer 配置就能验证。

含义：这是 Gemma 4 在 tool-bench 上跑得稳的物理原因，而不只是训练数据加得多。但同一作者也明确说："复杂多步推理和硬核 coding 我还是切去 Qwen3 Coder Next 或云端"——和 SWE-bench 数字一致。

结论：真 Gemma 4 在工具流稳定性上有架构层优势，但在代码生成能力上输给同尺寸 Qwen。

五、C 级：不采纳的常见说法

声称为什么不采纳
"Qwen 3.6 是开源里最接近 Opus 4.7 的" 只引一个 pelican SVG 案例，Simon 自己都说这个基准是玩笑。要证伪只能把所有 Opus 能做的任务都跑一遍——没人做过。
"Gemma 4 26B-A4B 在 24GB 卡上是 DOA" 纯情绪发言，作者没列任务、prompt、对照。事实上 150 tok/s 复现可证伪——而该说法没人复跑过。
"Qwen 3.6 在 SWE-bench 73.4% 说明它能替代付费 Claude" SWE-bench 已多次曝出训练集污染怀疑。要证伪只能拿 held-out 题集复测——Qwen 没开源他们的去污染流程。
"Gemma 4 是 reasoning 模型，强制 think，输出在 reasoning_content 里" 这部分是真的，但常被引用成"难用"——其实是 client 配置问题，关掉就行。归在 C 是因为大多数发帖人没说自己关过、就开始抱怨。
"Qwen 训了 pelican 的解" Reddit 半玩笑指控，无证据。要证伪要么找出原始训练集（不可能），要么用未公开的新基准复测（Simon 用了 flamingo+unicycle 复测，反指控不成立）。

六、综合画像：三个模型实际是什么

Gemma 4 26B-A4B-it

扎实不擅复杂代码

真实定位：日常 chat + 智能家居 + RAG + tool-calling 的"瑞士军刀"，多模态、256K 上下文、函数调用稳定。不是 SOTA 编码模型。

谁该用：要一个"啥都能干、不太掉链子"的本地大脑。

已知坑：默认 reasoning trace、MTP 头被官方阉割（限速）。

Qwen 3.5 35B-A3B

有独立验证已被 3.6 覆盖

真实定位：纯文本，最早的 Qwen3 系列 MoE 35B 旗舰；mlx-community 量化版有多轮 tool-use 退化 bug，GGUF/全精度无此问题。

谁该用：已经部署了不想换、或者想要稳定可引用的 baseline。

已知坑：mlx 4/8bit checkpoint，多轮 tool calling 第 5 / 13 轮起退化。

Qwen 3.6 35B-A3B

编码强分数易污染

真实定位：编码与 agentic 任务上目前同尺寸最强开源选项，多模态。SWE-bench 73.4 是真实测出，但抗污染基准上差距收窄。

谁该用：本地 coding agent / Claude Code 自托管替代。

已知坑：vLLM nightly streaming+MTP loop bug；早期社区报告多轮 tool 调用偶发遗漏上下文。

3.5 vs 3.6 该选哪个？

如果你只是看跑分：直接 3.6。
如果你要稳定的引用基线（论文、对照实验）：3.5 已有发表过的独立验证，3.6 还没有第二方完整复现。
如果你用 mlx-lm：等社区把量化路径修了再上 Qwen 任何版本，或走 GGUF。

七、给读者的一句话证伪习惯

看到模型评测先问三句：

  1. "硬件 + 量化 + prompt"三件套缺哪个？ 缺一个就是 B 级，缺两个就是 C 级。
  2. 基准是公开题集还是抗污染的（LiveCodeBench / Arena / 自己出题）？ 公开题集 + 厂商自报，分数无脑减 5-10 分。
  3. 报告人和模型方有没有关系？ 同生态合作伙伴的"评测"约等于 PR 稿。

最强的证据形式不是分数，而是 "我用同一台机器、跑同一个 prompt、用 model A 失败、换 model B 成功"——这是一句可以被任何人攻击的话，因此也是值得相信的话。
