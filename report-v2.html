一、v2 为什么还要试

v1 实验已经把四个最大旋钮（ncmoe、ub、threads、spec-type）调到了甜点。但还剩三个看似有空间的方向：

  1. KV cache 量化：当前 -ctk q8_0 -ctv q8_0，KV 占 ~1.4 GB 显存。如果能压到 q4_0 K，省 700 MB → ncmoe 从 30 降到 28 → 多 2 层专家在 GPU → gen 速度可能 +10-20%。
  2. cache-reuse：--cache-reuse 默认 0（关闭）。这个 flag 启用 KV shifting 算法，多轮对话理论上能几十倍提速。
  3. CUDA 环境变量：GGML_CUDA_FORCE_MMQ=1 在某些架构上能避开 cuBLAS 的 dequant 路径，提速 5-20%。

这三条都是"理论上能赚"，但 v2 全跑下来一条都不成立。下面分别说。

二、主线 1：KV cache 量化 —— q4/q5 触发 CUDA 慢路径

假设

llama.cpp 社区流传的经验：K 的量化对生成质量影响小（注意力分数被 softmax 平滑化），V 直接进残差流更敏感。所以"先牺牲 K、留 V 高精度"是常见做法。q4_0/q8_0 应该比 q8_0/q8_0 显存少 25% 但速度持平。

实测

ctk / ctvVRAM peak (MiB)Prompt evalWall (40K prompt + 200 gen)状态
f16 / f1614598821 tps53.6 s正常但比 q8 慢一点
q8_0 / q8_013507829 tps53.0 sv1 最优
q4_0 / q8_012820~37 tps超时（>600s, 55% 进度）慢 22 倍
q8_0 / q4_012707~25 tps超时（180s 内 0% 进度）慢 33 倍
q5_0 / q5_013709~30 tps超时（180s 内 0% 进度）慢 28 倍

因果链

q4_0 K 让 prompt eval 从 829 tps 直接掉到 30-40 tps（22-33× 变慢）。第一次跑 q4_q8 配置时，10 分钟内 40K prompt 只处理到 55%，被 curl 超时取消。后续两个非对称 / q5 配置同样卡死。

原因：llama.cpp 的 CUDA Flash Attention 内核对 KV 量化组合有 fast-path 限制。优化好的 mma kernel 只接受几个特定组合（f16/f16、q8_0/q8_0），其它组合（q4_0 K、q5_0 K、q8_0 K + q4_0 V 等）都会走通用的 dequant → matmul 慢路径。在 Qwen3-Next 的混合架构里，41 层中只有 10 层是 full attention，但这 10 层是性能热点。一旦 attention 的 K@Q 矩阵乘走慢路径，整次前向就被拖垮。

结论

在 RTX 4070 Ti SUPER + Qwen3-Next 这个组合上，q8_0/q8_0 就是 KV 量化的天花板。再压一档，速度从 829 tps 跌到 30-40 tps，等于不能用。社区那条"q4 K + q8 V"经验在这套硬件 + 这套模型上不成立。

三、主线 2：--cache-reuse —— 帮不上忙的是这个 flag

假设

llama-server 的 --cache-reuse N 默认 0（关闭）。这是免费的多轮场景提速——开启后，新 prompt 跟 slot 现有 KV 内容匹配的部分会在 KV 里做数学位移而不是重算。猜测 reuse=256 应该让连续问相似问题的 prompt eval 时间从几秒降到亚秒级。

实测设计

构造三轮对话：

  1. 请求 1：5K token 共享前缀 + 简单问题 1（~30 token 尾巴）
  2. 请求 2：同样的 5K 前缀 + 简单问题 2
  3. 请求 3：同样的 5K 前缀 + 200 token 额外上下文 + 简单问题 3

扫描 --cache-reuse ∈ {0, 256, 1024}。每轮在 server 端重新启动以确保 cache 状态对齐。

结果

cache-reuseTurn 1: prompt_n / wallTurn 2: prompt_n / wallTurn 3: prompt_n / wall
0（默认）4970 / 11.1s1026 / 4.5s1083 / 4.5s
256（推荐值）4970 / 11.9s1026 / 3.8s1083 / 4.3s
10244970 / 9.2s1026 / 3.7s1083 / 4.3s

三档 --cache-reuse 的 Turn 2/3 prompt_n 完全相同：1026 和 1083。说明命中前缀复用的根本不是 --cache-reuse。

因果链

真正起作用的是客户端 payload 里的 cache_prompt: true（已经默认开了）。

cache_prompt 处理严格前缀复用：新请求的 prefix 跟 slot 的 KV 内容 token-by-token 一致，那部分直接保留，只算后面的尾巴。Turn 2 跟 Turn 1 共享 5K 前缀 → 5K 几乎全保留，只算 ~30 token 的新尾巴。这就是为什么 Turn 2 wall 从 11 秒掉到 4.5 秒。

--cache-reuse N 处理的是不同的场景：non-strict prefix matching（KV shifting）。比如新 prompt 改了 system 中间一段（破坏了前缀严格匹配），但用户问题相同。这时 cache_prompt 帮不上忙、但 KV shifting 算法可以做"窗口滑动"找到子串匹配。我们的多轮聊天场景是严格前缀，用不到这条路径。

插曲：Turn 2 为什么不是 prompt_n=0？

Turn 2 共享了 5K 前缀，但 prompt_n 还有 1026 不是 0。原因：-ub 1024 让 KV cache 按 1024-token 块对齐。前缀+新尾巴的分歧点（"\n\nQ: Now list..." vs "\n\nQ: Summarize..."）落在最后一块的中间 → 整块从 4096 之后作废重算。4970 - 4096 + 新尾巴 ≈ 1026。

这是分块对齐的代价，跟 cache 算法无关，调小 -ub 能减少这个损失（但会让 prompt eval 慢 60%——不值得）。

结论

  • OpenAI-compatible 客户端默认开 cache_prompt，多轮聊天已经免费拿到 6× prompt eval 提速
  • --cache-reuse 这个 server flag 对本场景没用，保持默认 0 即可
  • 真的想看 KV shifting 起作用需要构造"system prompt 中间被改"的场景，本实验没测，但日常聊天场景碰不到

四、主线 3：GGML_CUDA 环境变量 —— Ada 上默认就是最优

假设

RTX 4070 Ti SUPER 是 compute capability 8.9（Ada Lovelace）。llama.cpp 的 CUDA 后端有几个运行时 flag，最优值跟架构相关，默认值未必对 Ada 最佳。社区在 Turing/Ampere 上的经验是 GGML_CUDA_FORCE_MMQ=1 能避开 cuBLAS 的 dequant 路径，提速 5-20%。

实测

环境变量Prompt tpsGen tpsWall (40K + 200)Draft 接受率结论
默认80246.155.0 s99.1%基线 ⭐
GGML_CUDA_FORCE_MMQ=1793 (-1%)41.6 (-10%)56.1 s97.3%gen 明显变慢
GGML_CUDA_FORCE_CUBLAS=179545.855.5 s98.2%等价默认
GGML_CUDA_DISABLE_GRAPHS=179246.555.6 s97.4%等价默认

因果链

FORCE_MMQ 让 gen 慢 10%：Ada 的 Tensor Cores 对 fp16 mixed-precision 已经高度优化（cuBLAS 默认走的就是 Tensor Core 路径）。MMQ 内核是 INT8 dp4a 路径，绕过 Tensor Cores → 反而更慢。这跟 Turing（无 Tensor Core for INT4）、Ampere（Tensor Core 但 mixed precision 不如 Ada）时代的经验相反。社区那条经验对 Ada 不适用。

FORCE_CUBLAS=1 等于默认：因为 llama.cpp 在这种 prefill workload 下默认就走 cuBLAS。这条 flag 只是去掉 auto-select 的 override，作用边际。

DISABLE_GRAPHS=1 完全没差：这是个意外但合理的发现 —— 说明这个配置下 CUDA Graphs 本来就没启用。MoE 的动态路由 + speculative decoding 的多分支 + flash attention 的可变 batch，三者一叠加，llama.cpp 自动停掉了 graph capture（因为 graph 要求每次执行的 kernel sequence 完全相同）。所以打开打关都一样。

结论

不要碰 CUDA env vars，让 llama.cpp 自己选路径。FORCE_MMQ 是 Ada 上的反向优化，剩下两个 flag 改了等于没改。如果未来换到 Hopper 或 Blackwell，这部分需要重测——架构变了内核路径选择规则也变。

五、综合结论：v1 配置就是最优

"全负面"为什么是好消息

  • 不用再花时间调 server 参数。剩下的旋钮我都试过了，没有更多空间。
  • 剩下的提速来源只有：
    • 换硬件（更大显存 → 更多专家直接在 GPU，不需要 ncmoe）
    • 等 llama.cpp 出新内核（比如 q4 KV cache 的 Tensor Core 实现 —— 那时 KV 量化会变成净收益）
    • 换模型量化（Q5_K_M、Q6_K）—— 但这是质量实验不是性能实验
  • 客户端层面唯一的免费午餐：确保用 cache_prompt: true（OpenAI shim 默认就是），多轮对话直接 6× prompt 提速。

未来需要重测的场景

这次结论绑定到当前硬件 + 模型 + 软件版本。如果以下任一变化，相关结论需要重测：

  • 换显卡到非 Ada 架构 → 主线 3（CUDA env vars）全部重测
  • llama.cpp 升级且 release notes 提到 KV cache 量化优化 → 主线 1 重测
  • 换模型架构（非 Qwen3-Next 的 SSM + MoE 混合）→ 主线 1 可能不同
  • 真的有用到非严格前缀的多轮场景（system prompt 频繁变更）→ 主线 2 需要单独构造场景重测
