Qwen3.6-35B-A3B v3 实验：MTP 草稿深度与 --fit 自动显存分配

实验日期：2026-05-24  ·  硬件：RTX 4070 Ti SUPER 16GB + Ryzen 5 5600 + 32GB RAM  ·  llama.cpp build b9297-b0df4c0cf  ·  模型：Qwen3.6-35B-A3B-heretic-MTP-GGUF（含 mmproj 视觉模块）

一句话总结：v1/v2 之后又冒出两条"还能再榨"的方向：把 MTP 的 --spec-draft-n-max 从 2 调大、或者干脆扔掉手写的 -ngl/-ncmoe 用 llama.cpp 的 --fit 自动分配。两条同样被实测证伪。本文记录两个错误假设、各自的实测数据，以及为什么 v1 的 (-ncmoe 30, --spec-draft-n-max 2) 在带视觉模型的工作负载下确实是甜点。

一、v3 为什么还要试

v2 已经把 KV 量化、cache-reuse、CUDA env vars 三条主流"应该会更快"的方向全部证伪。但还剩两个有理论依据的空间：

  1. MTP 草稿深度：当前 --spec-draft-n-max 2，每次只投机解码 2 个 token。把它调到 3 或 4，理论上单次接受率即使下降，总吞吐还能升 —— 因为一次验证 batch 能 commit 更多 token。
  2. --fit 自适应显存：手动 -ngl 999 -ncmoe 30 是 v1 拍脑袋调出来的，绑定到当时的 free VRAM。llama.cpp 内置 --fit + --fit-target 能根据实时可用显存动态决定 MoE 哪些层留 CPU、哪些上 GPU，理论上比手写更接近真实最优。

这两条同样在实测里被否决。下面分别说。

二、主线 1：--spec-draft-n-max 调大 —— MTP 接受率塌方

假设

投机解码的常见经验是：草稿深度 n 增加 → 单次接受率降低，但只要"期望接受 token 数 / 草稿成本"还在涨，吞吐就会涨。当前 n=2 时接受率 86–88%（v1 实测），通常 n=3 时仍能保持 75% 以上，所以期望接受数从 ~1.74 升到 ~2.3，理论上能给 decode 加 20–30%。

实测

测试方法：保持 v1 其它参数不变，只改 --spec-draft-n-max，用 25154-token 的真实带图 prompt（4.7 MB JSON，9 条消息含 4 张图）跑 bench.py，warmup 1 + 3 run，cache 命中模式下只测纯 decode。

--spec-draft-n-maxdecode TPS (3-run avg)min / maxdraft acceptance状态
2（v1 基线）52.552.0 / 52.90.858–0.886最优 ⭐
346.5 (-11%)42.7 / 48.70.788（恒定）慢且方差大
445.7 (-13%)42.5 / 48.20.780–0.824更慢

因果链

n=3/4 不仅没加速，反而比 n=2 慢 11–13%，方差从 ±0.5 t/s 放大到 ±3 t/s。接受率从 86–88% 直接塌到 78–82%。

原因：MTP 是单 head 模型，只能精确预测紧邻的下一个 token；再往后第 2、第 3 个草稿 token 都是"在前一个未验证草稿基础上的草稿"，置信度随深度指数级下降。这跟"独立小 draft 模型"投机解码的不一样 —— 独立 draft 模型每个 token 都是新前向的独立预测，深度增加损失温和；MTP 是同一组 hidden state 链式滚出的，深度增加直接撞天花板。

另一层成本：每多一个草稿 token 都要多跑一次 draft forward。对你的混合 GPU/CPU 推理布局来说，draft forward 的 latency 不可忽略（KV cache q8_0 + ncmoe 30 这种配置下，draft head 自己也要过一次 attention）。当接受率下降到 0.78，被拒绝的草稿就是纯浪费的草稿生成时间 + 拖累验证 batch 提前 break，所以 run-to-run 抖动从 ±0.5 t/s 放大到 ±3 t/s（验证经常在第 1/2 步就 break）。

结论

MTP 的 --spec-draft-n-max 不是越大越好，2 就是这个模型架构的硬上限。这条"独立 draft model 越深越好"的社区经验不能照搬到 MTP。如果以后换到双 head MTP（Qwen 3.5 Next 路线）或独立 draft 模型，这个上限可以重测；现在保持 n=2。

三、主线 2：--fit 自动分配 —— vision encoder 显存峰值没算进去

假设

llama.cpp 自带 --fit on（默认就是）+ --fit-target N（每张卡留 N MiB 余量），扫描合理的 ngl / cpu-moe 组合后挑一个"塞满显存但留 N MiB 安全余量"的配置。理论上比 v1 手写的 -ngl 999 -ncmoe 30 更接近实时最优 —— 因为 v1 的数字是当时桌面环境下拍脑袋调的，今天 free VRAM 可能不一样。

陷阱：手写参数让 --fit 静默 abort

v1 命令里同时有 -ngl 和 -ncmoe，--fit 实际上根本没运行。

看 common/fit.cpp:352-374：

if (mparams->n_gpu_layers != default_mparams.n_gpu_layers)
    throw ... ("n_gpu_layers already set by user, abort");
if (mparams->tensor_buft_overrides && ...)
    throw ... ("tensor_buft_overrides already set by user, abort");

只要 -ngl 或 -ncmoe 任一个被显式设置（后者通过 tensor_buft_overrides 起作用），--fit 立刻抛异常，被外层 catch 成一行 LOG_WRN。启动日志只会看到 fitting params to device memory ... 这一行，没有后续 abort 警告（取决于 verbosity 级别），让人误以为 fit 在工作。

所以想真正用 --fit 必须把 -ngl 999 -ncmoe 30 两个全部去掉，只留 --fit-target。

实测

配置decode TPSVRAM used / free (MiB)状态
手动 -ngl 999 -ncmoe 30（v1）52.5~15800 / ~500（实测启动 free VRAM 12554，加载后基本贴边）基线 ⭐
--fit-target 1500崩溃14822 / 1121clip image encode 申请 475 MiB 时 cudaMalloc failed → ggml_abort
--fit-target 250044.8 (-15%)13896 / 2047跑通但明显比手动慢

因果链

fit 1500 崩在 vision encoder。错误堆栈：

ggml_backend_cuda_buffer_type_alloc_buffer: allocating 475.56 MiB on device 0: cudaMalloc failed: out of memory
  in clip_image_batch_encode → ggml_backend_sched_alloc_graph → ggml_backend_tensor_alloc → ggml_abort()

--fit 算余量时只看 主模型权重 + KV cache + compute graph 估计，不知道 mmproj 的 vision encoder 在 image batch encode 时会一次性申请几百 MiB 临时 buffer。这个 prompt 里有 4 张图，clip 编码到最大一张时申请 475 MiB，把 fit 给主模型留的 1.5 GiB 余量挤穿（还要算上 KV cache 增长 + cache checkpoint，每个 80–90 MiB）。

fit 2500 跑通但慢 15%。fit 为了给 vision encoder 多留 2.5 GiB 安全余量，把更多 MoE 层留在 CPU —— VRAM 实际只用了 13896 MiB（比 v1 手动配置贴边的占用还少 ~2 GB）。GPU 留了空、CPU 多干活 → decode 从 52.5 t/s 掉到 44.8 t/s。

结论

当前 llama.cpp build 下，--fit 在带 mmproj 的视觉模型上不可用，要么 OOM 要么明显偏慢。

v1 拍脑袋调的 -ngl 999 -ncmoe 30 反而比 --fit 自动选的更激进、更优，原因是 v1 实测时已经把 vision encoder 的峰值显存隐式考虑进去（"加载后能跑通真实带图请求"就是 v1 的验收标准）。--fit 的内部模型还没把 mmproj 算进余量公式。

纯文本工作负载（无图、无 mmproj）下 --fit 应该能正常工作，本实验没覆盖这种场景。

四、综合结论：v1 配置在带视觉的工作负载下依然是最优

两条主线全负面：

v3 主线假设实测结果影响
MTP spec-draft-n-max 调大n=3/4 期望接受 token 更多 → decode 提速 20–30%接受率从 0.86 塌到 0.78，decode 反而慢 11–13%MTP 单 head 架构对深度敏感，n=2 是硬上限
--fit 自动显存分配比手写 -ngl/-ncmoe 更接近实时最优1500 余量直接崩；2500 余量慢 15%fit 公式不计 mmproj vision encoder 峰值
v1/v2/v3 三轮调优结论已经收敛。这套硬件 + 模型 + llama.cpp b9297 下的真正帕累托最优点： 
-ngl 999 -ncmoe 30 -b 2048 -ub 1024 -t 6 -tb 6 \
-ctk q8_0 -ctv q8_0 -ctkd q8_0 -ctvd q8_0 \
--spec-type draft-mtp --draft-p-min 0.75 --spec-draft-n-max 2
完整命令见 v1 报告第八节。

"全负面"为什么仍然是好消息

  • v3 又消掉两个可疑旋钮。三轮下来基本可以宣布"调参完成"，不再花时间扫描参数空间。
  • 暴露了 --fit 在带视觉模型场景下的一个真实缺陷：余量公式不计 vision encoder。这是个上游 issue 候选项（common/fit.cpp:504-532 那段 MoE 处理逻辑里完全没碰 mparams->use_mmap 之外的多模态分支）。
  • 暴露了 --fit 与 -ngl/-ncmoe 互斥时的静默 abort 行为。verbosity 不够高时用户不会看到任何提示，以为 fit 在跑实际上没跑 —— 这是个 UX bug。

未来需要重测的场景

v3 结论同样绑定到当前硬件 + 模型 + 软件版本。如果以下任一变化，相关结论需要重测：

  • 升级到能预测多 head 的 MTP 模型（如未来 Qwen 3.7 / 4.x 推出深度 ≥2 的 MTP）→ 主线 1 重测，n 上限可能变大
  • llama.cpp 升级且 release notes 提到 --fit 多模态支持 → 主线 2 重测
  • 换非视觉模型（纯 LLM、无 mmproj）→ 主线 2 可能本就成立，本实验未覆盖
  • 换显卡到 24 GiB+ 显存 → ncmoe 可大幅降低，--fit 在余量充足时崩溃概率下降，主线 2 的结论可能反转
