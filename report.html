Qwen3.6-35B-A3B 在 16GB 显卡上的 llama-server 调优实验

实验日期：2026-05-14  ·  硬件：RTX 4070 Ti SUPER 16GB + Ryzen 5 5600 + 32GB RAM  ·  llama.cpp build b9140

一句话总结：把一个 23 GB 的大模型塞进 16 GB 显卡，主要瓶颈不是显存，而是显存满了之后压在 CPU 上的那部分专家计算。通过四组对照实验，把每个能动的参数挨个验证一遍，最后做出来一份稳定不崩溃、prompt 处理速度比原始命令快 40% 的配置。

一、为什么这件事不简单

模型 Qwen3.6-35B-A3B 的权重文件有 23 GB，但 RTX 4070 Ti SUPER 只有 16 GB 显存。直接把模型扔上去会塞不下。简单的"放一半在显卡、放一半在内存"会带来明显的速度损失，因为模型每次推理都要在两边来回搬运数据。

幸运的是，这个模型是混合专家结构（MoE）——总共 256 个"专家"小模块，但每个 token 只激活其中 8 个。意思是：

  • 整个模型很大（23 GB），但每次实际用到的部分（约 3 GB 等效计算量）很小
  • 所以可以把"经常用到的部分"（注意力层、稠密层）放显卡，"偶尔用到的部分"（256 个专家）放内存
  • 关键是要切对地方——切错了，速度会暴跌

另外这个模型有混合注意力：41 层里只有 10 层是传统的全注意力，剩下 31 层是 Mamba 风格的"状态空间模型"。这意味着 KV 缓存（保存对话历史的那块显存）出奇地小（只有约 1.4 GB），不是瓶颈。真正的瓶颈是模型权重本身怎么分配。

能动的旋钮

参数能调什么对速度 / 显存的影响
-ngl / -ncmoe模型哪几层放显卡、哪几层的专家放内存影响最大，决定显存占用
-b / -ub处理 prompt 时一次喂给模型多少个 token影响 prompt 处理速度
-t / -tb用几个 CPU 线程影响在 CPU 上的专家计算速度

-ctk / -ctv对话历史用多少精度压缩影响 KV 缓存显存

二、实验方法（控制变量怎么做的）

每一轮只改一个参数，其它全部固定，跑相同的 prompt，记录三个核心指标：

  1. VRAM peak：跑完一次推理过程中显存的最高占用。这个数 + headroom（剩余空间）决定稳不稳，剩太少容易在某些 prompt 下崩。
  2. Prompt tps：每秒能"读"多少个 token。比如 40000 token 的长 prompt，如果是 1000 tps，要 40 秒才能读完才开始回答。
  3. Gen tps：每秒能"写"多少个 token。30 tps 大约是流畅阅读速度；70 tps 是非常快的流式输出。

跑的脚本和原始日志都留在 /tmp/llama-bench/，每个 phase 一个 CSV，可以自己复核。

三、Phase 1：显存边界扫描

问题

把多少层专家放 CPU（-ncmoe N）才合适？放太多 → GPU 闲、推理慢；放太少 → 显存炸。先找出"刚好能装下"的位置。

做法

固定其它所有参数（128K 上下文、KV 用 q8_0 压缩、投机解码开启），把 -ncmoe 从 20 到 41 扫一遍，每个值都跑一次推理观察显存峰值和速度。

因果链

ncmoe 越小（放显卡上的专家越多）→ 显存用得越满 → 速度越快，但越接近爆显存的红线。ncmoe=26 是稳定的最佳点：还剩 2.2 GB 显存余量给突发情况（更长 prompt、桌面环境、浏览器），同时性能几乎不输给更激进的 ncmoe=24。

四、Phase 2：批处理 / 线程

问题

处理 prompt 时，模型一次能"吃"多少 token？线程开多少？

做法

固定 ncmoe=26，跑一段 40000 token 的长 prompt + 200 token 回答，扫四组配置。

因果链

  • 微批 -ub 从 512 提到 1024 → prompt 处理快 66%。 因为每次同时处理更多 token，对 GPU 更友好，开销摊得更薄。代价是多占 ~1 GB 显存（在 ncmoe=26 的 headroom 内可承受）。
  • 批 -b 再往上调到 3072 没有更多收益。 ub 已经吃饱了显卡，b 主要是更高层的调度参数，作用边际。
  • 线程开到 12（用超线程）反而让生成速度慢 38%。 因为 6 核 12 线程的 Ryzen 5 5600，两个超线程在同一个物理核上抢同一份 L1 缓存和向量计算单元，对密集 SIMD 工作负载（专家矩阵乘法）是反效果。只用物理核 -t 6 -tb 6。

五、Phase 3：投机解码（MTP）值不值

问题

"投机解码"是让模型先草拟几个 token、再批量验证的技术。原始命令开了 MTP（这个模型自带的"草拟头"），但 n-max 该设多少？要不要关掉？

做法

固定其它参数（ncmoe=26、ub=1024、t=6），扫 --spec-draft-n-max 从 0（关闭投机解码）到 4。

结果

n_maxVRAM peakPrompt tpsGen tps草稿接受率总耗时（40K+200）
0（关闭）13726101351.9—44.0 s
11496289056.3100%49.2 s
2（你原始的设置）1496390857.298%48.3 s
31496391950.295%48.2 s
41477291655.296%48.0 s

反直觉的发现

对你"长 prompt + 短输出"的场景，投机解码反而是个净亏损。

看 n_max=0（关闭）vs n_max=2（你原本设置）：
  • 关闭：prompt 1013 tps，回答 51.9 tps，总耗时 44 秒，VRAM 多省 1.2 GB
  • 开启：prompt 908 tps（慢 10%），回答 57.2 tps（快 10%），总耗时 48 秒
投机解码在 prompt 处理阶段加了约 5% 开销（要同时跑主模型和草拟头），在生成阶段才能省回来。只有当输出超过约 250 个 token 时，省下的 gen 时间才能盖过加上的 prompt 开销。

建议

  • 主要做"读长文档 → 给短答案"（RAG、长文摘要、问答）→ 用 --spec-type none，更快也更省显存
  • 主要做长回答（写代码、写文章、思考链推理 thousands of tokens）→ 保留 --spec-type draft-mtp --spec-draft-n-max 2
  • n_max 改到 3 或 4 没有显著好处，反而草稿接受率降到 95%

六、Phase 4：带视觉模块的 heretic 怎么调

问题

heretic 模型多了一个 mmproj 视觉模块（约 860 MiB），全部在显卡上。这意味着比 havenoammo 要多腾出 ~1 GB 显存。

做法

用 Phase 1-3 的最优参数（-ub 1024 -t 6 -tb 6 --spec-draft-n-max 2），扫 ncmoe ∈ {28, 30, 32}。

结果

ncmoe=30（比 28 更保守）反而比 ncmoe=28 略快。原因猜测：28 把 VRAM 用到 14.4 GB，留给 GPU 调度的临时空间太紧；30 留下 2.4 GB，调度器可以更高效地分配中间张量。最重要的是，30 留出了足够的余量，是稳定首选。

结论修正

  1. 你原始命令的 VRAM 用量、gen 速度跟我推荐的几乎一样——-fitt 1536 已经在做自动 offload 了

    • -ub 1024 → 长 prompt 处理快 ~65%
    • 显式 -ncmoe 30 → heretic（带视觉）不再 OOM 崩溃
    • 建议关闭 MTP（如果是短回答场景）→ 再快 10%

九、术语小词典

VRAM（显存）
显卡上专用的内存。显卡只能"看到"显存里的数据，CPU 内存里的数据要先搬过去才能用。本机 16 GB。
Token
模型处理文本的最小单位。一个中文字大约 1-2 token，一个英文单词大约 1 token。32K context 大概是 5-10 万汉字。
Context length（上下文长度）
模型一次能"看到"的对话内容长度。越长能看到的越多，但占的显存也更多。本实验都用 128K。
KV cache（KV 缓存）
对话进行中模型保留的历史中间结果。每说一句话就追加一点，不需要每次重新算。占用随上下文长度线性增长。
MoE（混合专家）
一种模型结构。把一层网络拆成几百个小"专家"，每个 token 只激活 8 个。总参数大，实际计算量小。
Offload（卸载）
把模型的一部分权重放在 CPU 内存而不是显卡上。代价是模型计算时要在两边来回搬数据，速度变慢。
Prompt eval
模型读你输入的过程。读完之前不会开始回答。tps 越高 → "首字延迟" 越短。
Generation（生成 / gen）
模型写答案的过程。tps 越高 → 流式输出越流畅。30 tps 是阅读速度，70 tps 已经很快。
Speculative decoding（投机解码）
用一个小的"草拟器"先猜接下来几个 token，再让大模型批量验证。猜对的几个 token 一起出，省时间。猜错就丢掉重来。
MTP（Multi-Token Prediction）
模型自带的"草拟头"。比再训一个独立的小模型简单，但仅限于 MTP-aware 的模型。本实验的 Qwen3.6-35B-A3B-MTP 就是这种。
n-max
投机解码一次猜几个 token。本实验测下来 2 是最佳，再高接受率下降反而变慢。
OOM（Out Of Memory）
显存或内存不够，程序直接崩。本实验 heretic 的原始命令就是 OOM 崩了。
Q4_K_XL / Q8_0
量化精度。Q4 把每个数字压成 4-bit（一字节装两个），Q8 是 8-bit。压得越狠模型越小、显存越省，但精度有损失。
Auto-fit (-fitt)
llama.cpp 的自动 offload 功能。指定一个目标"剩多少显存"，llama.cpp 会自动决定模型放多少层在显卡。
ncmoe
显式指定"把多少层的专家放 CPU"。和 auto-fit 互斥，但对 MoE 模型更精确——只搬专家、保留注意力在 GPU。
